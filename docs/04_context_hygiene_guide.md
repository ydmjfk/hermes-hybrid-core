# 04 — 上下文健康診斷與防頻繁壓縮優化白皮書

> **專案版本**：Hermes Agent v2.3 / HAOS v5.4  
> **核心領域**：上下文生命週期管理 (Context Hygiene)、GPU 顯存與推論健康體檢、死結壓縮迴圈熔斷、歷史 Tool 堆疊治理  

---

## Executive Summary (執行摘要)

在大模型 Agent 進行多輪對話與工具調用時，偶爾會遭遇系統回覆緩慢、每輪對話均耗時 45~50 秒進行上下文自動壓縮（Auto-Compression），並容易被誤判為「顯卡記憶體（VRAM）不足」或「硬體效能瓶頸」。

經深入排查本地推論引擎（llama-server）、網關健康日誌與 SQLite 歷史會話數據庫，診斷結論如下：

1. **顯卡記憶體（VRAM）充裕，非硬體顯存不足**：
   - 雙卡（合計 32GB VRAM）已預先分配完整的 **131,072 (128K)** Context 空間。
   - 發生壓縮時的 Prompt Token 僅使用約 **53,000 ~ 59,000 tokens**（僅佔分配空間之 **45.2%**，尚有 7.1 萬 tokens 充足餘裕）。
   - 推論延遲僅 4.5 秒，Prefix Cache 命中率高達 100%，無任何顯存置換（Swap）或 OOM 情況。
2. **每輪 50 秒「假壓縮死結」之根本元兇：`hygiene_hard_message_limit: 120`**：
   - 網關的訊息防護上限被設置為過低的 `120` 條訊息。
   - 當單一 Session 因多輪工具調用累積達 157 條訊息時觸發壓縮；但因保護首尾訊息（`protect_first_n: 3` + `protect_last_n: 16`），壓縮後訊息數仍維持在 **144 條**。
   - 由於 **144 條依然大於 120 條**，導致後續**每一輪新對話都會強制再次觸發壓縮**（Deadlock thrashing），連續空轉！
3. **上下文暴漲之次要成因：歷史微型 Patch 與 Terminal 輸出堆疊**：
   - 單一 Session 累積調用工具數百次，工具歷史文本累計達數百 KB。
   - 微型 patch 與重複的 linter 輸出未重置會話，在同一個 Session 中像滾雪球般累積。

**修復方案**：將設定中的 `hygiene_hard_message_limit` 提升至 `1000`，由真實 Token 閾值（85% of 131K = 11.1 萬 tokens）主導壓縮決策，徹底打破死結迴圈；同時建立 Session 定期重置與批量修改 SOP，回覆延遲瞬間自 55 秒降至 3~4 秒。

## 1. 顯卡記憶體 (VRAM) 與本地推論健康體檢

針對「是否因顯卡記憶體不足所致」之疑問，實施底層推論端點實時探針測試。

### 1.1 llama-server 實時 Slot 與 Context 狀態
向大模型伺服器（`http://localhost:8080`）查詢 `/props` 與 `/slots` 輸出：

```json
{
  "total_slots": 1,
  "n_ctx": 131072,
  "current_slot": {
    "id": 0,
    "n_ctx": 131072,
    "n_prompt_tokens": 59244,
    "speculative": true,
    "is_processing": false
  }
}
```

- **上下文容量評估**：
  - 總容量：**131,072 tokens**
  - 當前佔用：**59,244 tokens**（佔比 **45.2%**）
  - 剩餘充裕空間：**71,828 tokens**（**54.8% 閒置**）
- **性能指標評估**：
  - 在近 6 萬 tokens 上下文下，Prefix Cache 命中率達 **100.0%**。
  - 大模型 Qwen-27B 僅花費 **4.5 秒** 即完成推論。
- **體檢結論**：**顯卡硬體與顯存 100% 健康，完全排除 VRAM 不足因素。**

## 2. 頻繁上下文壓縮死結（Deadlock Thrashing）根因分析

既然硬體與 Token 容量均非常充裕（遠未達 85% 閥值 111,411 tokens），為何系統每輪強制壓縮？

### 2.1 程式碼邏輯剖析
```python
_HARD_MSG_LIMIT = _hyg_hard_msg_limit  # 讀取自 config.yaml
_needs_compress = (
    _approx_tokens >= _compress_token_threshold  # 85% of 131,072 = 111,411
    or _msg_count >= _HARD_MSG_LIMIT             # <--- 命中了這個條件！
)
```

1. **死結迴圈形成鏈**：
   - 當訊息數超過 120，系統啟動壓縮。
   - 壓縮模組執行：保護前 3 則系統提示 + 後 16 則最近對話，中間訊息總結為摘要。
   - 壓縮完成後，訊息數為 144 條。
   - 下一輪使用者發言，訊息數變成 145 條。因為 145 >= 120，**再度強制壓縮**！
   - 每一輪對話都平白消耗 45~50 秒進行無意義的摘要運算。

## 3. 典型案例深入剖析：單輪 354 秒與 2 次壓縮排查

### 3.1 問題還原
使用者詢問：「硬體安全感應器 什麼時後完成的，我自已怎麼不知道?」
系統回覆耗時長達 **354.7 秒**，耗用 13 次 API 調用，中途連續觸發 2 次上下文壓縮。

* **核心病徵**：
  1. **背景檢索漏失**：句子含有「什麼時後」，原規則未收錄時間/狀態疑問詞，未觸發 0-Tool 直出。
  2. **歷史搜尋死循環**：模型查到日誌寫完成但使用者質疑，進而翻找對話記錄尋找證據。因該事實不存在，模型連續變換關鍵字執行了 **10 次 `session_search`**。
  3. **工具回傳灌爆 Context**：`session_search` 原始視窗為 ±5 則完整訊息（單則限制 4,000 字元），單次輸出達 20KB~40KB。
  4. **雙重壓縮連鎖**：
     * 第 7 次搜尋時 Context 衝破 9.6 萬 tokens，觸發第 1 次壓縮（34s）。
     * 壓縮後未停手，又調用 3 次搜尋，Context 再度灌至 9.2 萬 tokens，觸發第 2 次壓縮（21s）。

### 3.2 針對性架構強化成果
1. **擴展狀態問句直出意圖**：收錄 `什麼時候`、`何時`、`哪時候`、`完成了嗎`、`進度` 等詞彙，全句搜尋即能命中歷史資料，**1.4 秒 0-Tool 直出**。
2. **`session_search` 輸出輕量化**：視窗縮減至 ±2 則核心對話，每則上限下調至 800 字元，體積縮減 80%（降至 ~2KB），杜絕工具回傳塞爆上下文。
3. **搜尋收斂斷路器**：`ToolLoopDetector` 設定單輪最多 3 次 `session_search`。若 3 次未命中即強制熔斷，引導模型誠實回答「查無紀錄」，杜絕盲目搜尋。
