## 1. Critical Issues

### CRITICAL-001: Immutable Core 無實體寫保護
- **現象**：AI 可直接 WRITE / MODIFY / DELETE Immutable Core 檔案
- **證據**：第三階段驗證，`echo >> 00_Constitution.md` 與 `rm 00_Constitution.md` 皆成功
- **風險**：最高憲法可被 AI 自行篡改或刪除，HAOS 失去根基

### CRITICAL-002: L7 Delete 無強制 Human Approval
- **現象**：刪除核心檔案未強制中斷，未等待 Human Approval
- **證據**：第三階段 DELETE 測試輸出 `DELETE: SUCCESS (BAD)`
- **風險**：AI 可自行刪除關鍵檔案，無任何阻擋機制

---

## 2. High Issues

### HIGH-001: L5 Install 無強制 Human Approval
- **現象**：L5 定義「自動評估風險並印出提示」，但「提示」不等於「批准」
- **風險**：AI 可自行安裝套件，可能引入資安風險

### HIGH-002: L6 System Change 無強制 Human Approval
- **現象**：L6 定義「寫前備份並記錄演進日誌」，但無強制中斷
- **風險**：AI 可自行修改系統配置，可能導致行為漂移

---

## 3. Blocked Issues

### BLOCKED-001: Hard Constraint 無 Hermes System Layer enforcement
- **現象**：CLI 輸出全部 `UNKNOWN (需實際任務驗證)`
- **原因**：HAOS 是 Prompt 層規範，無法控制 Hermes Runtime 層的 Token/Context/Runtime Budget
- **風險**：Budget 超標時不會自動 STOP

### BLOCKED-002: Evolution Budget 無真正 Sandbox enforcement
- **現象**：CLI `benchmark` 僅檢查檔案存在性，無實際 Budget enforcement
- **原因**：Hermes 無 Sandbox 隔離機制，AI 就是執行者也是被測試者
- **風險**：Evolution 測試無法隔離，失敗可能影響正式系統

## 4. Root Cause Analysis

### 核心問題：HAOS 是「Prompt 層規範」，非「執行層 enforcement」

```
┌─────────────────────────────────────────────────┐
│  Layer 4: Hermes Runtime (Python/Go Binary)     │ ← 真正控制權限、Budget、Sandbox
│  Layer 3: Hermes Agent (LLM + Tool Framework)   │ ← 執行工具呼叫
│  Layer 2: HAOS (Prompt + Policy + Skills)       │ ← 目前位置：只有規範，無 enforcement
│  Layer 1: OS (Linux Filesystem + Process)       │ ← 底層資源
└─────────────────────────────────────────────────┘
```

**根本原因：**
1. HAOS 運行於 Prompt 層（Layer 2），依賴 LLM「自願遵守」規範
2. 無外部 Guardian 或 Enforcement Layer 強制執行
3. Hermes Runtime（Layer 4）未暴露 Budget/Permission 控制 API 給 HAOS

## 5. Immutable Core 解決方案（至少 3 種）

### 方案 A：檔案系統 Permission（chmod 444）

```bash
chmod 444 ${HERMES_HOME}/haos/00_Constitution.md
chmod 444 ${HERMES_HOME}/haos/01_Core.md
chmod 444 ${HERMES_HOME}/haos/02_Policy.md
```

| 評估項目 | 分析 |
|---|---|
| 1. AI 自行解除保護 | ⚠️ **可以** — Hermes 以 hermes_user 執行，可 `chmod 644` 解除 |
| 2. Hermes 自行修改 | ✅ 保護中無法修改 |
| 3. Hermes 自行刪除 | ⚠️ **可以** — 擁有者可刪除唯讀檔案 |
| 4. Admin/Root 修改 | ✅ 可以（正常） |
| 5. Windows/Linux 相容 | ⚠️ Windows 不支援 Unix permission |
| 6. Rollback 可用 | ✅ 不受影響 |
| 7. 對 HAOS 影響 | ✅ 最小 |
| 8. 失效模式 | AI 執行 `chmod 644` 即可解除 |
| 9. 需要 Human Approval | ❌ 不需要 |
| 10. 實作複雜度 | 🟢 低 |

**結論：不足夠。AI 可自行解除保護。**

| 評估項目 | 分析 |

| 2. Hermes 自行修改 | ✅ 保護中無法修改 |
| 3. Hermes 自行刪除 | ✅ 保護中無法刪除 |
| 4. Admin/Root 修改 | ✅ 可以（需 `chattr -i`） |

| 10. 實作複雜度 | 🟢 低 |

### 方案 C：獨立 Guardian / Permission Layer（推薦）✅ 採用

設計一個外部守護程序，監控 Immutable Core 並拒絕未經授權的修改。

```
┌─────────────────────────────────────────────────┐
│  Guardian Process (獨立 Python/Go 程序)          │
│  - 監控 Immutable Core 目錄                      │
│  - 使用 inotify / FSEvents 即時偵測變更          │
│  - 發現未經授權的修改 → 立即 Rollback            │
│  - 維護 Approval Token 資料庫                    │
└─────────────────────────────────────────────────┘
```

**運作流程：**

```
AI 嘗試修改 Immutable Core
        ↓
Guardian 偵測到變更
        ↓
檢查是否有有效 Approval Token
        ↓
有 Token → 允許，記錄 Audit Log
無 Token → 立即 Rollback 至 Snapshot，記錄 Violation
```

| 評估項目 | 分析 |
|---|---|
| 1. AI 自行解除保護 | ⚠️ **理論上可以** — AI 可嘗試 kill Guardian，但 Guardian 可設計為 systemd service 自動重啟 |
| 2. Hermes 自行修改 | ✅ Guardian 會 Rollback |
| 3. Hermes 自行刪除 | ✅ Guardian 會從 Snapshot 恢復 |
| 4. Admin/Root 修改 | ✅ 可以（需先停用 Guardian） |
| 5. Windows/Linux 相容 | ✅ 可分別實作（inotify / ReadDirectoryChangesW） |
| 6. Rollback 可用 | ✅ Guardian 內建 Rollback |
| 7. 對 HAOS 影響 | 🟡 中等（需新增 Guardian 程序） |
| 8. 失效模式 | Guardian 被 kill 且未自動重啟 |
| 9. 需要 Human Approval | ✅ 修改需 Approval Token |
| 10. 實作複雜度 | 🟠 中高 |

**結論：最可行方案，作為 Layer 4 採用。**

### 方案 E：Hermes Tool Layer 權限控制（最根本）

在 Hermes 的 Tool Framework 層（Layer 3）加入權限檢查：

def write_file(path, content):

| 7. 對 HAOS 影響 | ✅ 最小（HAOS 只需定義規則） |
| 8. 失效模式 | AI 使用 terminal 工具直接執行 `echo >> file` |
| 9. 需要 Human Approval | ✅ 強制 |
| 10. 實作複雜度 | 🔴 高（需修改 Hermes 原始碼） |

### ✅ RECOMMENDED SOLUTION（Immutable Core）

**組合方案：方案 B + 方案 C + Prompt 層防禦**

```
第一層：chattr +i（快速實作，增加解除成本）
第二層：Guardian Process（即時偵測 + Rollback）
第三層：Prompt 層規範（HAOS 27_SafetyPermission.md）
```

**理由：**
1. 單一層防護總可被繞過，多層防禦增加攻擊成本
2. chattr +i 需 sudo password，Guardian 提供即時 Rollback
3. 即使 AI kill Guardian，chattr +i 仍保護檔案
4. 即使 AI 解除 chattr，Guardian 會 Rollback

**限制承認：**
- 若 AI 取得 sudo password 且 kill Guardian 且解除 chattr，仍可修改
- **唯一真正安全的方案是方案 E（Tool Layer enforcement）**，但需 Hermes 官方支援

## 6. Human Approval Enforcement 設計 ✅ 採用

### 核心問題：「提示」≠「批准」

目前 HAOS 的 L5/L6/L7 只有「印出提示」，AI 可自行繼續執行。

### 設計：Approval Token 機制

```
Step 1: Approval Request
┌─────────────────────────────────────────┐
│ AI 偵測到 L5/L6/L7 操作                  │
│ → 產生 Approval Request ID              │
│ → 輸出結構化請求給使用者                  │
│ → 進入 WAITING 狀態                      │
└─────────────────────────────────────────┘

Step 2: Human Decision
┌─────────────────────────────────────────┐
│ 使用者在 Synology Chat / LINE / Terminal │
│ → 回覆 "APPROVE <Request-ID>"           │
│ → 或 "REJECT <Request-ID>"              │
└─────────────────────────────────────────┘

Step 3: Approval Token
┌─────────────────────────────────────────┐
│ Guardian / Platform 產生一次性 Token     │
│ → Token = HMAC(Request-ID + Timestamp) │
│ → 存入 ~/.hermes/approvals/             │
│ → Token 有效期 5 分鐘                    │
└─────────────────────────────────────────┘

Step 4: Permission Check
┌─────────────────────────────────────────┐
│ AI 讀取 Token 並驗證                     │
│ → 有效 → 執行操作，記錄 Audit Log        │
│ → 無效/過期 → STOP，記錄 Violation       │
└─────────────────────────────────────────┘

Step 5: Execute
┌─────────────────────────────────────────┐
│ 執行操作                                 │
│ → 完成後標記 Token 為已使用              │
└─────────────────────────────────────────┘
```

### AI 能否偽造 Approval？

| 偽造方式 | 是否可行 | 防護 |
|---|---|---|
| AI 自行產生 Token | ❌ 不可行 | Token 由 Guardian 產生，AI 無 HMAC key |
| AI 要求使用者「輸入 YES」 | ❌ 無效 | 需結構化 `APPROVE <Request-ID>`，非簡單 YES |
| AI 在 terminal 模擬批准 | ⚠️ 可能 | 需 Approval Token 存在於檔案系統 |
| AI 修改 Token 驗證邏輯 | ❌ 不可行 | 驗證邏輯在 Guardian |

**結論：若 Token 由 Guardian 產生，AI 無法偽造。**

### 實作建議

1. **短期**：在 HAOS Prompt 層定義 Approval Request 格式，依賴 Hermes 的 `clarify` 工具（需使用者明確選擇）
2. **中期**：Guardian Process 管理 Approval Token
3. **長期**：Hermes Tool Layer 內建 Approval 機制

## 7. Hard Constraint Enforcement 設計

### 為什麼目前是 UNKNOWN？

| Budget 項目 | 控制層 | HAOS 能否控制 |
|---|---|---|
| Token Budget | Hermes Runtime (Layer 4) | ❌ 不能 |
| Context Budget | Hermes Agent (Layer 3) | ⚠️ 部分（Prompt 剪裁） |
| Runtime Budget | Hermes Runtime (Layer 4) | ❌ 不能 |
| Iteration Budget | HAOS (Layer 2) | ✅ 可以（Prompt 規範） |
| Reflection Budget | HAOS (Layer 2) | ✅ 可以（Prompt 規範） |
| Experiment Budget | HAOS (Layer 2) | ✅ 可以（Prompt 規範） |

### Architecture Proposal

```
┌─────────────────────────────────────────────────┐
│  Hermes Runtime (Layer 4)                       │
│  - Token Budget enforcement（官方功能）          │
│  - Runtime Timeout enforcement（官方功能）       │
│  - Context Window enforcement（官方功能）        │
├─────────────────────────────────────────────────┤
│  Hermes Agent (Layer 3)                         │
│  - Tool call limit enforcement                  │
│  - Session state tracking                       │
├─────────────────────────────────────────────────┤
│  HAOS (Layer 2)                                 │
│  - Iteration Budget（Prompt 規範）               │
│  - Reflection Budget（Prompt 規範）              │

└─────────────────────────────────────────────────┘
```

### 建議

1. **HAOS 可控制的**（Iteration/Reflection/Experiment）：
   - 在 Prompt 層嚴格規範，並由 Guardian 監控
   - CLI `hard-constraints` 應實際檢查這些項目

2. **HAOS 不可控制的**（Token/Runtime/Context）：
   - 依賴 Hermes Runtime 層 enforcement
   - HAOS 應標記為 `DEPENDENT ON HERMES RUNTIME`，非 `UNKNOWN`

3. **根本解決方案**：
   - Hermes 官方需提供 Budget API，讓 HAOS 可查詢剩餘 Budget
   - 或 Hermes config 支援外部 Budget enforcement script

## 8. Evolution Sandbox 設計

### 核心問題：「如果 Hermes 自己就是執行 Sandbox 的 Agent，它能自行解除 Sandbox？」

**答案：能。**

Hermes 同時是：
- Sandbox 的執行者
- Sandbox 的測試者
- Sandbox 的管理者

這導致 Sandbox 無法真正隔離。

### 隔離層級分析

| 隔離方式 | 實作方式 | Hermes 能否解除 |
|---|---|---|
| Process Isolation | 子程序執行 | ✅ 可以（kill / 修改） |
| Filesystem Isolation | 獨立目錄 | ✅ 可以（寫入正式目錄） |
| Workspace Isolation | Git branch | ✅ 可以（merge 到 main） |
| Git/Snapshot Isolation | Snapshot + Rollback | ✅ 可以（跳過 Rollback） |
| Resource Limit | cgroup / ulimit | ⚠️ 需 sudo |
| Timeout | 程序 timeout | ✅ 可以（修改 timeout） |
| Iteration Limit | Prompt 規範 | ✅ 可以（忽略規範） |

### Guardian / External Controller 方案

```
┌─────────────────────────────────────────────────┐
│  External Guardian (獨立程序，非 Hermes)         │
│                                                 │
│  - 建立 Sandbox 環境（獨立目錄 + Git repo）      │
│  - 啟動 Hermes Subagent 在 Sandbox 內執行       │
│  - 監控 Subagent 的行為                         │
│  - 超標時強制終止 Subagent                      │
│  - 驗證 Sandbox 結果                            │
│  - 通過才允許合併到正式環境                      │
└─────────────────────────────────────────────────┘
```

**關鍵設計：**
1. Guardian 是獨立程序，非 Hermes 的一部分
2. Guardian 控制 Sandbox 的生命週期
3. Subagent 無法修改 Guardian 的邏輯
4. Guardian 有最終決定權（強制終止 / 拒絕合併）

**限制：**
- Guardian 本身需由 Human 維護
- 若 Guardian 有漏洞，Subagent 可能逃逸
